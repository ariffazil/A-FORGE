## The Agentic Design

**The chaos was:** AGENTS.md files claimed tool counts that didn't match live `list_tools` outputs. WEALTH said "37+6=43" but returned 50. A-FORGE said "79" but returned 99. GEOX had 49 backward-compat aliases unmarked. The drift was manual — humans wrote the docs, organs emitted the data, and they diverged silently.

**The agentic insight:** distinguish STATIC from DYNAMIC. An agent knows:
- The **contract** (schema, organs list, canonical floors) doesn't drift — it's the law
- The **state** (tool count, health, status) drifts constantly — it must be observed
- A SOT that conflates the two becomes either out-of-date (if static) or uninterpretable (if dynamic)

**The fix:** two files, one job each.

| File | What it holds | Edit cadence |
|---|---|---|
| `SOT_SCHEMA.json` | The contract: organs, floors, status taxonomy, MCP protocol version | F13 action only (versioned, immutable between ratifications) |
| `ARIFOS_SOT_LIVE.json` | Live state: per-organ tool count, health, status, drift | Regenerated by `sot_publish.py` (cron daily) |

`SOT_SCHEMA.json` is the static. `ARIFOS_SOT_LIVE.json` is the dynamic. `sot_publish.py` is the bridge.

These are the things that **must not drift without F13 ratification**:
- The 7 organs (adding an 8th is a constitutional decision, not a code commit)
- The 13 floors (F1-F13 are the law; new floors are a 888_HOLD)
- The MCP protocol version (we don't casually change wire formats)
- The transport type

Anything else in the SOT is dynamic.

## What's DYNAMIC (live state)

```json
{
  "last_verified_utc": "2026-07-08T16:11:39.419920+00:00",
  "schema_drift": ["arifOS/arif_init: unmarked", ...],
  "unreachable_organs": ["GEOX"],
  "organs": {
    "arifOS":   {"tool_count": 12, "canonical_count": 0, "status": "healthy", ...},
    "A-FORGE":  {"tool_count": 99, "canonical_count": 0, "status": "healthy", ...},
    "WEALTH":   {"tool_count": 50, "canonical_count": 50, "status": "healthy", ...},
    "WELL":     {"tool_count": 18, "canonical_count": 0, "status": "degraded", ...},
    ...
  }
}
```

These are the things that **drift naturally**:
- Tool count (organs add/remove tools)
- Per-tool canonical/deprecated status (lifecycle of features)
- Per-organ health (organs go up/down)
- Identity hash (regenerated on each build)
- Last-verified timestamp

The SOT captures them as observations, not as claims.

## Per-Tool Status Taxonomy

| Status | Meaning | Lifecycle |
|---|---|---|
| `canonical` | Current, supported, public | Promote to deprecated when feature changes |
| `deprecated` | Still callable, will be removed | Remove after migration window |
| `experimental` | New, not stable | Promote to canonical after soak period |
| `unmarked` | **DRIFT** — not yet classified | Action required: classify or remove |

**The unmarked state is the chaos signal.** It means: nobody's decided yet. It's the agent's job to surface this so humans (or other agents) can decide.

## Why This Design Works

| Property | How it's enforced |
|---|---|
| **The contract never drifts silently** | `SOT_SCHEMA.json` is versioned (`arifos.sot/v1`); F13 only changes version |
| **The state is always fresh** | `sot_publish.py` regenerates from live organ probes; no human editing |
| **Drift is visible** | Every unmarked tool appears in `dynamic_state.schema_drift`; the federation can act on it |
| **AGENTS.md can't lie** | When `sot_emit_agents.py` is built, the doc regenerates from the SOT, not from human memory |
| **Adding an organ is a constitutional decision** | The organ list in `SOT_SCHEMA.json` is a F13 action; the schema enforces it |
| **One source of truth, one place to look** | `ARIFOS_SOT_LIVE.json` is THE place; everything else is generated |

## The Single Invariant

> **Live state must be derived, never maintained. The schema is law. The data is observation. They never confuse roles.**

If you find yourself hand-editing `ARIFOS_SOT_LIVE.json`, you're doing it wrong. Regenerate via `sot_publish.py`. If the script doesn't capture what you need, extend the schema (F13), then extend the script. Never edit the data.
