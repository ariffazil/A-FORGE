## CROSS-CUTTING ANALYSIS

### The `zen-` Prefix Problem

Every skill starts with `zen-`. In conversation, agents will drop it. "Load body" instead of "Load zen-body". When that happens, you lose the family grouping. The prefix is doing two jobs: (1) family membership, (2) philosophical framing. It does (1) well but (2) is noise — no agent loading `zen-body` is thinking about Zen Buddhism. They're checking if the containers are running.

**Recommendation:** The prefix is acceptable but not optimal. It creates a clean namespace (`zen-*`) which is useful for tooling and search. But it adds 4 characters of noise to every invocation. If the federation grows to 20+ skills, the prefix becomes a tax.

### The Discoverability Gap

The weakest scores are all in Discoverability. `zen-order` (5), `zen-terrain` (5) — these are the names that lose the most from the rename. An agent searching for "entropy" or "skill atlas" would have found the old names instantly. The new names optimize for elegance over findability.

**Mitigation:** Add aliases. Register `entropy-thermo-zen` as an alias for `zen-order`. Register `meta-mesa-skill-atlas` as an alias for `zen-terrain`. The canonical name is clean; the alias preserves discoverability.

### The Semantic Overlap Triangle

Three skills form a protective cluster:
- `zen-body` — senses (health, drift, containers)
- `zen-guard` — monitors (continuous, autonomic)
- `zen-gate` — blocks (point-of-entry, immune)

The boundary between "sense" and "monitor" is blurry. And "guard" vs "gate" are phonetically and semantically close. A new agent loading `zen-guard` when they need `zen-gate` (or vice versa) is a real risk.

### The Layer Collision Risk

Two names collide with Layer 3 concepts:
- `zen-witness` ↔ Witness (Zen Organ 6)
- `zen-forge` ↔ A-FORGE (execution organ)

This is *intentional* — the operational skills implement the constitutional principles. But it creates ambiguity in documentation and conversation. "The witness said HOLD" — is that zen-witness (the skill) or the Witness organ (the constitutional layer)?

## VERDICT: USE_WITH_RESERVATIONS

**Rationale:**

The scheme is **good, not great.** The best names (`zen-forge`, `zen-witness`) are excellent — they're clear, memorable, and conceptually aligned. The worst names (`zen-order`, `zen-terrain`) sacrifice too much discoverability for elegance.

The `zen-` prefix creates clean namespacing but adds noise. The semantic overlap between `zen-guard` and `zen-gate` needs resolution. The layer collisions with Witness and A-FORGE need documentation.

**Use it** — it's a significant improvement over the current chaos of `entropy-thermo-zen`, `meta-mesa-skill-atlas`, and `tool-creation-gate`. But apply these fixes:

1. **Add aliases** for the low-discoverability names (zen-order, zen-terrain)
2. **Document the guard/gate boundary** explicitly in both skills
3. **Add a naming convention note** explaining that `zen-X` implements Zen Organ X or A-FORGE capability X
4. **Consider renaming `zen-order`** — it's the weakest name. `zen-entropy` would be more honest, even if less elegant.
